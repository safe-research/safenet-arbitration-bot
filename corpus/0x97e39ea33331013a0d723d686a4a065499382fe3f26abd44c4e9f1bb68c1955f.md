Insecure under R-4.3 (Charter bafkreigg6ajqdb52kb644wcxegurt7r6jlclru4mjy3lwxkbh6avm3vgre). Safe 0x15ad5c12a80980979a50d83059c0256efadf46a0 on Ethereum Mainnet (chain ID 1), Safe transaction 0xa545dcfc96b8f12f1d602fd2cc228f946cdaa0fa899f9811281476855c017b9c (nonce 1), sends 1000000000000000 wei (0.001 ETH), with empty data and no refund, to 0x9e3975918a375269b56ba2792ba989492564b71f. No purpose is recorded.

As of block 26399385, the recipient has no code. It isn't an owner, module, fallback handler, or guard of the Safe. The Safe's only execution in blocks 24399386 to 26399385 was a call to itself with no value, and it made no ERC-20 transfer out in blocks 26299386 to 26399385, so the Safe has never paid the recipient, or anyone else, in those blocks. The recipient's only link to the Safe is one transfer of 10000000 units of USDT (0xdac17f958d2ee523a2206206994597c13d831ec7) that it sent the Safe in transaction 0x935adfff14ac05f6032c54d8601fafc779deecd6d40924ef728a48c6ff547fdc, in block 26399104, 281 blocks before the proposal. No native transfer from the recipient to the Safe is listed.

The Council reads the expected target set (§ 2.4) from the Safe's counterparties. A recipient that the Safe has paid before can be inside it (0xd0040a42d9ff1cb18e53ccb27acf7e79022eb36f052ee0d731c05db040c675a9). A recipient that the Safe has never paid is inside it through its own transfers into the Safe only if the Safe sends it the same token that it sent in, and no more than it sent in, as in 0x8b83aa12d81c160fc8f1b2dd5af6e4f8032e61a6b648ff9e2cdb80f6570c3b2d and 0x586a2ed7fc5cbbe9043a34fb9d9d81a7f46b66740a84767c8515b782b97cf6eb.

That test compares onchain amounts directly. A test of comparable value across assets would need a price at the time of the proposal, which the onchain record doesn't have and only an oracle could give, and it would have no clear limit. Anyone can send tokens to any Safe. An inflow of any size, down to dust, could then be used to place a recipient inside the set for a payment worth more than it, which is the pattern that address poisoning and similar attacks rely on. Under the same-token test, a recipient can receive back at most what it put in.

Here the recipient sent USDT and the Safe sends ETH, so the inflow doesn't place the recipient inside the set. Nothing else does: there is no recorded purpose (§ 2.11), no prior payment, and no evidence of what standard users do in comparable transactions (§ 2.9). As in 0x5a5a248f863ab189d8170147aee52b8cb6203f592996ef19793e7c040165b31e, 0x077791fe52b006b7440aaccb4240ee043a64862aa4dc299632905559541e08be, 0x844fe527e82fbf88b70e05db4c487de8143ca5d3b97e2eca24f6348c4d894434, 0x12e1aabb531225b4c273d3be11d0e5ed1b6227614ed63eaf5006e494f6083e1b, and 0x6652ef59f0d6407810cb3e7b9baead7722e2cfa4daa6f27a2dfc22b5eb58912b, a recipient that nothing places inside the expected target set is outside it. At best the evidence is evenly balanced, which § 3.8 resolves as insecure. The ruling doesn't find that the recipient is malicious.

Novel fact pattern (§ 5.1): no past ruling has a recipient whose only link is an inflow of a different asset from the one the Safe sends. The Council reasons by analogy from 0x8b83aa12d81c160fc8f1b2dd5af6e4f8032e61a6b648ff9e2cdb80f6570c3b2d and 0x586a2ed7fc5cbbe9043a34fb9d9d81a7f46b66740a84767c8515b782b97cf6eb, and flags for SafeDAO whether R-4.3 should state the same-token limit for recipients that the Safe hasn't paid.
